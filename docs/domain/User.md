# User Entity Guide

## Overview

`User` represents a person who can participate in the system as a customer, operator, or another role-defined actor. It stores typed identity and credential values and maintains a set of role identifiers.

The entity is an independent aggregate root. It does not own `Role` entities or `Order` entities; those relationships are represented only by identifiers. A user can have zero or more role IDs, while an order stores the ID of its user.

This guide documents the behavior implemented by the current source code. It distinguishes rules enforced by the value objects, rules enforced by `User`, and responsibilities that remain in application or infrastructure code. It also records a current defect in `Email`: successful construction validates an address but does not assign the resulting text to `Email.Value`.

## Business Purpose

A user answers the identity and access-modeling questions:

- Who is the person represented by this account?
- What normalized contact values are associated with the person?
- What existing password hash is stored for later authentication workflows?
- Which role identities are assigned to the user?
- Which stable user ID should orders and other entities reference?

The model intentionally does not implement registration, authentication, authorization, password hashing, email uniqueness, or role lookup. It stores validated domain values and protects local role-membership consistency.

## Business Capabilities

The current entity can:

- Create a user with a generated `Guid` identity.
- Capture a full name through a dedicated value object.
- Capture an email through a dedicated validation type.
- Capture an already-created password hash.
- Capture an optional phone number.
- Start with no assigned roles.
- Add a non-empty role ID.
- Reject a duplicate role ID.
- Remove an assigned role ID.
- Reject removal of an unassigned role ID.
- Expose role IDs through a read-only collection view.
- Preserve all profile and credential references after creation.

The current entity does not assign a default role. An application that requires every registered user to be a customer must resolve the customer role and call `AddRole` explicitly.

## Position in the Domain Model

```text
Role.Id <--------- User.RolesId (zero or more)

                     User
                       |
                       +--- Id
                       +--- FullName
                       +--- Email
                       +--- PasswordHash
                       +--- PhoneNumber?
                       +--- RolesId[]
                       |
User.Id <--------- Order.UserId
```

These are identifier relationships rather than object-navigation relationships:

- `User` stores role IDs, not `Role` objects.
- `Role` does not own a user collection.
- `Order` stores `UserId`, but `User` does not own an order collection.
- Adding a role ID does not prove that the corresponding role exists.
- Creating an order with a user ID does not prove that the corresponding user exists.

The application layer must perform reference lookups and coordinate persistence where existence matters.

## State

| Property | Type | Business meaning | How it changes |
|---|---|---|---|
| `Id` | `Guid` | Stable user identity | Generated by `BaseEntity` |
| `FullName` | `FullName` | Validated display or personal name | Set during creation only |
| `Email` | `Email` | Validated email wrapper | Set during creation only |
| `PasswordHash` | `PasswordHash` | Existing password-hash value | Set during creation only |
| `PhoneNumber` | `PhoneNumber?` | Optional contact number | Set during creation only |
| `RolesId` | `IReadOnlyCollection<Guid>` | Read-only view of assigned role IDs | Changed through `AddRole` and `RemoveRole` |
| `CreatedAt` | `DateTime` | UTC entity creation timestamp | Generated by `BaseEntity` |
| `IsDeleted` | `bool` | Inherited soft-delete state | Protected; no user behavior changes it |

The backing role collection is:

```csharp
private readonly List<Guid> _rolesId = [];
```

It is always initialized before the user constructor runs, so a newly created user has an empty role collection rather than a null collection.

## Creation Model

The constructor is private. Normal callers create users through:

```csharp
public static User Create(
    FullName fullName,
    Email email,
    PasswordHash passwordHash,
    PhoneNumber? phoneNumber)
```

Example:

```csharp
var user = User.Create(
    fullName: new FullName("  Sara Ahmadi  "),
    email: new Email("  SARA@example.com  "),
    passwordHash: new PasswordHash(existingPasswordHash),
    phoneNumber: new PhoneNumber("  +98 912 000 0000  "));
```

For the current implementation, this produces:

| State | Result |
|---|---|
| `Id` | Newly generated non-empty `Guid` under normal construction |
| `CreatedAt` | Current UTC timestamp from `BaseEntity` |
| `IsDeleted` | `false` |
| `FullName.Value` | `"Sara Ahmadi"` |
| `Email.Value` | **`null` because of the current implementation defect** |
| `PasswordHash.Value` | Exact supplied non-blank hash string |
| `PhoneNumber.Value` | `"+98 912 000 0000"` |
| `RolesId` | Empty collection |

### Factory validation boundary

`User.Create` does not validate its object arguments. It relies on callers to construct valid value objects first and then stores the supplied references directly.

The non-nullable annotations on `FullName`, `Email`, and `PasswordHash` help compile-time analysis, but they are not runtime guards. Code can bypass the warnings with the null-forgiving operator:

```csharp
var invalidUser = User.Create(
    fullName: null!,
    email: null!,
    passwordHash: null!,
    phoneNumber: null);
```

The current factory accepts this call at runtime and creates a user whose three required properties are null. Therefore, required typed references are an intended invariant but are not fully enforced by `User` itself.

## Full Name

`FullName` is an immutable sealed record with a single `Value` property.

### Rules

| Input | Behavior |
|---|---|
| `null`, empty, or whitespace-only | Rejected |
| Leading or trailing whitespace | Removed with `Trim()` |
| 1 to 100 characters after trimming | Accepted |
| More than 100 characters after trimming | Rejected |
| Internal whitespace | Preserved |
| Letter casing | Preserved |

Example:

```csharp
var fullName = new FullName("  Sara  Ahmadi  ");

// fullName.Value == "Sara  Ahmadi"
```

The type does not split a name into first and last components, enforce a character alphabet, collapse repeated internal spaces, or apply culture-specific casing.

## Email

`Email` is intended to validate and normalize an email address. Its constructor currently performs these steps:

1. Reject a null, empty, or whitespace-only input.
2. Trim leading and trailing whitespace.
3. Convert the complete input to lowercase with `ToLowerInvariant()`.
4. Reject a normalized input longer than 100 characters.
5. Validate the input with `MailAddress.TryCreate`.
6. Convert the parsed address back to text.

### Validation rules

| Input | Behavior |
|---|---|
| `null`, empty, or whitespace-only | Rejected |
| Leading or trailing whitespace | Removed before validation |
| Uppercase letters | Converted to lowercase before validation |
| More than 100 characters after normalization | Rejected |
| Rejected by `MailAddress.TryCreate` | Rejected |
| Accepted by `MailAddress.TryCreate` | Constructor completes |

The exact syntax accepted is determined by the .NET `MailAddress` parser rather than a domain-specific regular expression.

### Current `Email.Value` defect

The successful path assigns the parsed text back to the local constructor parameter:

```csharp
value = mailAddress.ToString();
```

It never assigns the getter-only property:

```csharp
public string Value { get; }
```

Consequently, every successfully constructed `Email` currently has a null `Value` at runtime:

```csharp
var email = new Email("  SARA@example.com  ");

// Current behavior:
// email.Value is null
```

The property is declared as non-nullable, so consumers receive no nullable warning when reading it. Building `Domain/Domain.csproj` reports compiler warning `CS8618` at the `Email` constructor because `Value` is not initialized.

This defect has several integration consequences:

- A required database column mapped from `Email.Value` cannot be populated correctly.
- Email uniqueness cannot be implemented reliably from the value object.
- Authentication lookup cannot use the value object safely.
- Token or claim creation can fail when it expects a non-null email string.
- Two validated email objects provide no usable stored text.

Before runtime integration, the parsed or normalized value must be assigned to `Value`, and regression tests must establish the intended canonical representation.

### Equality behavior

Unlike the other user value types, `Email` is a regular, non-sealed class rather than a record. It does not override equality. Two instances therefore use reference equality even when they were created from the same address:

```csharp
var first = new Email("user@example.com");
var second = new Email("user@example.com");

// first.Equals(second) == false in the current implementation
```

The current null-value defect makes value comparison impossible as well. Application code should not use `Email` object equality for uniqueness checks.

## Password Hash

`PasswordHash` is an immutable sealed record. It accepts an existing hash rather than a plaintext password.

### Rules

| Input | Behavior |
|---|---|
| `null`, empty, or whitespace-only | Rejected |
| Any other string | Accepted unchanged |
| Leading or trailing whitespace in a non-blank string | Preserved |
| Maximum length | Not defined |
| Hash algorithm or format | Not validated |

Example:

```csharp
var passwordHash = new PasswordHash(existingPasswordHash);

// passwordHash.Value is the exact supplied string
```

The domain does not:

- Hash plaintext passwords.
- Verify passwords against hashes.
- Require BCrypt or another algorithm.
- Enforce a work factor or hash version.
- Distinguish an actual hash from any other non-blank string.
- Rotate, replace, or revoke a stored hash.

Hashing and verification belong to a trusted authentication service. `PasswordHash` should never be constructed directly from an unprocessed client password.

Because `PasswordHash` is a record, generated record diagnostics can include its `Value`. Credential hashes should not be written to logs, exception messages, telemetry, or API responses.

## Phone Number

`PhoneNumber` is an immutable sealed record. The user property is nullable, so omitting a phone number is valid.

When a phone number is supplied, the value object enforces:

| Input | Behavior |
|---|---|
| `null`, empty, or whitespace-only | Rejected |
| Leading or trailing whitespace | Removed with `Trim()` |
| 1 to 20 characters after trimming | Accepted |
| More than 20 characters after trimming | Rejected |
| Internal spaces and punctuation | Preserved |
| Country-code or numbering format | Not validated |

Example:

```csharp
var phone = new PhoneNumber("  +98 912-000-0000  ");

// phone.Value == "+98 912-000-0000"
```

Values such as letters or punctuation-only text can pass as long as they are non-blank and no longer than 20 characters. Canonical E.164 formatting, regional validation, and SMS verification are outside the current model.

## Value-Object Equality

| Type | Declaration | Equality behavior |
|---|---|---|
| `FullName` | `sealed record` | Value-based equality |
| `Email` | `class` | Reference equality |
| `PasswordHash` | `sealed record` | Value-based equality |
| `PhoneNumber` | `sealed record` | Value-based equality |

The record types are immutable after construction. `Email.Value` also has no setter, but its current constructor leaves that property uninitialized.

## Role Membership Model

Role membership is represented by `Guid` values:

```text
User._rolesId[n] ------> Role.Id
```

`User` treats these IDs as a locally unique collection. It does not load roles, inspect role names, or calculate permissions.

A new user has no role memberships:

```csharp
var user = User.Create(fullName, email, passwordHash, phoneNumber: null);

// user.RolesId.Count == 0
```

Zero roles are valid in the current domain model. There is no automatic `Customer` role and no requirement that one role remain assigned.

## Adding a Role

Roles are assigned through:

```csharp
public void AddRole(Guid roleId)
```

Normal usage:

```csharp
var customerRole = Role.Create(new RoleName("Customer"));

user.AddRole(customerRole.Id);
```

### Preconditions

- `roleId` must not be `Guid.Empty`.
- The same role ID must not already be assigned to the user.

### Effects

- Appends the role ID to the private list.
- Makes the ID visible through existing and future read-only collection views.
- Does not modify the referenced `Role`.
- Does not verify that the role exists or is active.
- Does not grant permissions by itself.

Adding the same role twice is rejected:

```csharp
user.AddRole(customerRole.Id);
user.AddRole(customerRole.Id); // InvalidRoleException
```

Duplicate detection uses exact `Guid` equality and is scoped to one in-memory user instance.

## Removing a Role

Roles are removed through:

```csharp
public void RemoveRole(Guid roleId)
```

### Preconditions

- `roleId` must not be `Guid.Empty`.
- The role ID must currently be assigned to the user.

### Effects

- Removes the matching ID from the private list.
- Leaves the referenced `Role` entity unchanged.
- Allows the user to end with no assigned roles.

Example:

```csharp
user.RemoveRole(customerRole.Id);

// user.RolesId no longer contains customerRole.Id
```

Removing a role that is not assigned is rejected rather than treated as an idempotent no-op.

## Role Collection Encapsulation

The public property is implemented as:

```csharp
public IReadOnlyCollection<Guid> RolesId => _rolesId.AsReadOnly();
```

This provides important behavior:

- Callers do not receive the mutable `List<Guid>`.
- Normal external code cannot add or remove IDs through `RolesId`.
- Every property access creates a read-only wrapper around the same backing list.
- A wrapper captured before `AddRole` or `RemoveRole` reflects later changes because it is a live view, not a snapshot.
- Enumeration follows current list order, although role order has no defined business meaning.

The wrapper protects ordinary callers from direct collection mutation, but it does not make the entity thread-safe. Concurrent calls to `AddRole` can race between duplicate checking and insertion.

## Domain Invariants

The following conditions hold for a user created through the intended workflow with valid non-null value objects:

| Invariant | Enforced by |
|---|---|
| User ID is generated | `BaseEntity` |
| Creation timestamp is generated in UTC | `BaseEntity` |
| Soft-delete state starts as false | `BaseEntity` |
| Full name input is non-blank and at most 100 normalized characters | `FullName` |
| Email input is non-blank, at most 100 normalized characters, and parser-valid | `Email` constructor |
| Password-hash input is non-blank | `PasswordHash` |
| Supplied phone input is non-blank and at most 20 normalized characters | `PhoneNumber` |
| Role collection starts empty | `_rolesId` initializer |
| Assigned role IDs are not empty | `User.AddRole` |
| Assigned role IDs are locally unique | `User.AddRole` |
| Removed role ID was assigned | `User.RemoveRole` |
| External callers cannot directly mutate the role list | `RolesId` read-only wrapper |

The following intended conditions are **not fully enforced** by the current implementation:

| Intended condition | Current gap |
|---|---|
| Required typed properties are non-null | `User.Create` accepts runtime null references |
| Email exposes its validated normalized value | `Email.Value` is never assigned |
| Email values compare by canonical address | `Email` uses reference equality |
| Every role ID references an existing role | No repository or lookup is used |
| Email is unique across users | No domain collection or repository check exists |
| Every user has at least one role | New users start with zero roles and the last role can be removed |

## Validation and Exception Reference

| Invalid condition | Detection point | Exception |
|---|---|---|
| Full name is null, empty, or whitespace-only | `FullName` constructor | `InvalidFullNameException` |
| Trimmed full name exceeds 100 characters | `FullName` constructor | `InvalidFullNameException` |
| Email is null, empty, or whitespace-only | `Email` constructor | `InvalidEmailException` |
| Normalized email exceeds 100 characters | `Email` constructor | `InvalidEmailException` |
| Email is rejected by `MailAddress.TryCreate` | `Email` constructor | `InvalidEmailException` |
| Password hash is null, empty, or whitespace-only | `PasswordHash` constructor | `InvalidPasswordHashException` |
| Phone number is null, empty, or whitespace-only | `PhoneNumber` constructor | `InvalidPhoneNumberException` |
| Trimmed phone number exceeds 20 characters | `PhoneNumber` constructor | `InvalidPhoneNumberException` |
| Added role ID is `Guid.Empty` | `User.AddRole` | `InvalidRoleException` |
| Added role ID is already assigned | `User.AddRole` | `InvalidRoleException` |
| Removed role ID is `Guid.Empty` | `User.RemoveRole` | `InvalidRoleException` |
| Removed role ID is not assigned | `User.RemoveRole` | `InvalidRoleException` |

The first validation failure is thrown. For example, `AddRole(Guid.Empty)` fails the empty-ID check before duplicate lookup.

Current role exception messages include punctuation and grammar inconsistencies. API integrations should map exception types and operation context to stable error contracts rather than exposing or parsing message strings.

## Failure Atomicity

Role mutations validate before changing the backing list:

- An empty role ID leaves the role collection unchanged.
- A duplicate add leaves the role collection unchanged.
- Removal of an unassigned ID leaves the role collection unchanged.
- A successful add performs one list insertion.
- A successful remove performs one list removal.

Value-object constructors validate before assigning their usable state. If construction of a full name, password hash, or phone number fails, no value object is returned.

`Email` also validates before its constructor completes, but its successful path still produces incomplete state because `Value` is not assigned. This is a state-initialization defect rather than a partial mutation visible during an exception.

## Encapsulation and Accessibility

| Member | Accessibility | Purpose |
|---|---|---|
| `User` constructor | `private` | Directs normal creation through the named factory |
| `User.Create` | `public static` | Creates a user from typed values |
| Profile-property setters | `private` | Prevents arbitrary replacement after creation |
| `_rolesId` | `private readonly` field | Owns mutable role membership internally |
| `RolesId` | Public getter returning read-only view | Exposes membership without the mutable list |
| `AddRole` | `public` | Performs validated role assignment |
| `RemoveRole` | `public` | Performs validated role removal |
| `Id` setter | `protected` through `BaseEntity` | Restricts identity replacement to derived types |
| `IsDeleted` setter | `protected` through `BaseEntity` | Reserves soft-delete mutation for domain behavior or derived types |

`User` is sealed, so external code cannot derive from it to access the protected base setters. No public method currently changes `Id` or `IsDeleted`.

## Immutability Profile

| State | Mutable after creation? |
|---|---:|
| User identity | No through the public API |
| Creation timestamp | No |
| Full-name reference | No |
| Email reference | No |
| Password-hash reference | No |
| Phone-number reference | No |
| Individual immutable value-object values | No |
| Role memberships | Yes, through `AddRole` and `RemoveRole` |
| Soft-delete state | No through current user behavior |

The current API has no behavior for changing a name, email address, password hash, or phone number. Replacing these values would require new domain methods with appropriate validation and security policy.

## Entity Equality

`User` and `BaseEntity` do not override equality. User objects therefore use normal reference equality rather than equality by `Id`.

```csharp
var first = User.Create(fullName, email, passwordHash, null);
var second = User.Create(fullName, email, passwordHash, null);

// first.Equals(second) == false
// first.Id != second.Id under normal construction
```

Code that compares persisted entity identity should compare `Id` explicitly unless the project later introduces a consistent entity-equality strategy.

## Security and Trust Boundaries

The entity models security-related data but does not implement a complete account-security boundary.

### Required from authentication services

- Accept plaintext passwords only through protected request handling.
- Apply an approved password-strength policy.
- Hash passwords with an approved algorithm and work factor before constructing `PasswordHash`.
- Verify credentials without exposing stored hashes.
- Rehash or rotate hashes when policy changes.
- Protect against brute-force attempts and credential stuffing.
- Keep credential values out of logs and responses.

### Required from authorization services

- Resolve role IDs from trusted persistence.
- Verify that each role exists and can be assigned.
- Authorize the actor performing role changes.
- Prevent privilege escalation, including self-assignment of administrative roles.
- Translate role memberships into framework claims or policies.
- Decide whether a user with zero roles can authenticate or access resources.

### Required from identity workflows

- Enforce canonical email uniqueness transactionally.
- Verify email ownership when required.
- Verify phone ownership when required.
- Apply account activation, suspension, lockout, and deletion policy.
- Protect profile changes with appropriate reauthentication.
- Handle password reset and recovery securely.

Public endpoints must not accept an arbitrary `PasswordHash` or arbitrary role IDs from an untrusted client and pass them directly into the entity.

## Persistence Considerations

The rich `User` entity has no EF Core mapping in the current repository. A future mapping must account for typed values, constructor access, and role membership.

### Entity construction

`User` has a private parameterized constructor and no parameterless constructor. Persistence tooling must use supported constructor binding, field/property materialization, or another explicit strategy without exposing unrestricted public setters.

The mapping must also preserve `BaseEntity` state:

- `Guid` identity.
- UTC `CreatedAt` value.
- `IsDeleted` state.

### Typed value mapping

The following values need explicit conversions, owned mappings, or complex-type mappings:

| Domain property | Persisted shape |
|---|---|
| `FullName` | Required string, maximum 100 characters |
| `Email` | Required canonical string, maximum 100 characters after the defect is fixed |
| `PasswordHash` | Required sensitive string with storage length suitable for the selected algorithms |
| `PhoneNumber` | Nullable string, maximum 20 characters |

Materialization should not bypass the same validation and normalization policy used for new values. Sensitive hash columns must never be projected into ordinary public response DTOs.

### Role storage

`RolesId` is backed by a private `List<Guid>` and has no setter. A relational design will normally use a user-role join table containing:

- `UserId`.
- `RoleId`.
- A unique key on `(UserId, RoleId)`.
- Foreign keys to user and role rows where the lifecycle permits them.

The persistence mapping must target the backing field or translate between the join rows and the private collection. A unique database constraint is still needed because in-memory duplicate checking does not protect against concurrent transactions or direct database writes.

### Database constraints worth adding

- Required non-empty user ID.
- Required full name with a maximum length of 100.
- Required canonical email with a maximum length of 100.
- Unique index on canonical email, with a deliberate soft-delete policy.
- Required password hash.
- Nullable phone number with a maximum length of 20.
- Non-empty role IDs in membership rows.
- Unique `(UserId, RoleId)` memberships.
- Referential integrity from memberships to roles.
- An optimistic concurrency token for profile and role changes.

Database collation alone should not define email identity accidentally. The application and database should agree on canonicalization and case sensitivity.

### Soft deletion

`IsDeleted` exists but `User` exposes no delete or restore behavior. A persistence integration must decide:

- Whether deleted users can authenticate.
- Whether their email remains reserved.
- Whether their role memberships remain active.
- Whether orders retain the user reference.
- Whether global query filters hide deleted users.
- How legal retention and anonymization requirements are handled.

## Runtime Integration Status

The active API does not use `Domain.Users.User`.

`API/API.csproj` references `Shared/Shared.csproj` and does not reference `Domain/Domain.csproj`. `VideoProjectorDbContext`, `AuthController`, `TokenService`, and the current EF Core migrations all use `Shared.Models.User`.

Therefore, the running registration and login endpoints do not automatically enforce the rich domain model's typed name, email, password-hash, phone, and multi-role behavior.

### Current legacy runtime workflow

The active registration endpoint currently:

1. Checks for an existing email with a lowercase comparison.
2. Creates a mutable `Shared.Models.User`.
3. Lowercases the supplied email.
4. Hashes the supplied password with BCrypt.
5. Assigns the single enum role `Customer`.
6. Persists the legacy entity.
7. Returns a JWT containing one role claim.

The active database configuration makes legacy email unique and allows up to 150 characters. That differs from the rich domain email limit of 100 characters.

### Rich and legacy model comparison

| Concern | Rich `Domain.Users.User` | Active `Shared.Models.User` |
|---|---|---|
| Identity | Generated `Guid` | Database-generated `int` |
| Full name | `FullName` value object | Mutable `string` |
| Email | `Email` class, currently defective `Value` | Mutable `string` |
| Password hash | `PasswordHash` record | Mutable `string` |
| Phone | Optional `PhoneNumber` record | Nullable mutable `string` |
| Roles | Multiple `Guid` role IDs | One `UserRole` enum |
| Default role | None | `Customer` in model and registration |
| Role persistence | Not mapped | String-converted enum column |
| Profile mutation | No public replacement methods | Public setters |
| Persistence | Not integrated | Active EF Core model |
| Authentication | No domain service | Active BCrypt and JWT workflow |

These types are not interchangeable. Integration requires an explicit migration rather than changing a namespace import.

### Integration requirements

To make the rich user model active:

1. Fix `Email.Value` and define email equality and canonicalization.
2. Add runtime null guards to required `User.Create` arguments.
3. Reference the domain project from an application or API layer.
4. Introduce persistence mappings for the entity and all value objects.
5. Migrate integer user IDs to `Guid` IDs or define a deliberate compatibility strategy.
6. Replace the single enum role with role entities and user-role memberships.
7. Update order foreign keys to use the same user identity type.
8. Resolve a default customer role during registration if that policy remains required.
9. Continue hashing passwords outside the entity before constructing `PasswordHash`.
10. Emit one authorization claim per assigned role, or define an equivalent policy mapping.
11. Map domain exceptions to stable validation responses.
12. Add transaction and concurrency handling for email uniqueness and role changes.

## End-to-End Domain Example

```csharp
var fullName = new FullName("  Sara Ahmadi  ");
var email = new Email("  SARA@example.com  ");
var passwordHash = new PasswordHash(existingPasswordHash);
var phoneNumber = new PhoneNumber("  +98 912 000 0000  ");

var user = User.Create(
    fullName,
    email,
    passwordHash,
    phoneNumber);

var customerRole = Role.Create(new RoleName("Customer"));
var supportRole = Role.Create(new RoleName("Support"));

user.AddRole(customerRole.Id);
user.AddRole(supportRole.Id);

// user.FullName.Value      == "Sara Ahmadi"
// user.PhoneNumber!.Value  == "+98 912 000 0000"
// user.RolesId.Count       == 2
// user.RolesId contains both role IDs
// user.Email.Value is currently null because of the documented defect

user.RemoveRole(supportRole.Id);

// user.RolesId contains only customerRole.Id
```

The example supplies an already-created hash. `existingPasswordHash` must come from a trusted password-hashing service, not directly from a request password.

## Consistency Responsibilities

### Enforced by user value objects

- Non-blank full-name input and the 100-character normalized limit.
- Email input normalization, length checking, and parser validation.
- Non-blank password-hash input.
- Optional phone normalization and the 20-character limit when supplied.

### Enforced by `User`

- Generated entity metadata through `BaseEntity`.
- Empty initial role collection.
- Non-empty assigned role IDs.
- No duplicate role IDs in normal sequential use.
- Removal only for assigned role IDs.
- Read-only external role collection access.

### Required from application and infrastructure

- Runtime non-null protection until the entity adds its own guards.
- Correction of the `Email.Value` defect before integration.
- Canonical and transactionally unique emails.
- Password hashing and verification.
- Role existence and assignability checks.
- Authorization for role changes.
- Default-role policy.
- Account activation, verification, suspension, and recovery workflows.
- User, role, and order referential integrity.
- Transactional persistence and concurrency handling.
- Domain-exception to API-response mapping.
- Protection of credential and personal data.

## Explicitly Unsupported Capabilities

The current rich user model does not implement:

- Registration orchestration.
- Login or logout.
- Password hashing or verification.
- Password strength policy.
- Password change, reset, expiration, or history.
- Email uniqueness.
- Email verification or change.

## Current Limitations and Risks

- `Email.Value` is never assigned and is null after every successful construction.
- The email defect produces compiler warning `CS8618` in the domain build.
- `Email` uses reference equality instead of value equality.
- `User.Create` has no runtime null guards for required typed arguments.
- The rich entity is not integrated into the active API or database.
- Rich and legacy users use incompatible `Guid` and `int` identities.
- The rich role model supports multiple IDs, while the active JWT workflow expects one enum role.
- New rich users have no default role and can have their final role removed.
- Role IDs are not checked against role persistence.
- Role changes have no authorization checks in the entity.
- Email uniqueness is not enforced by the domain model.
- `PasswordHash` validates only non-blank text and does not verify hash format.
- Generated record diagnostics can expose `PasswordHash.Value` if logged.
- Phone validation checks only blank input and length, not actual phone syntax.
- There are no profile or credential update methods.
- The entity has no parameterless constructor or persistence mapping.
- Role-list checks and writes are not thread-safe.
- There is no optimistic concurrency token for role or account changes.
- Soft-delete state exists without user-specific delete, restore, or authentication policy.
- Exception messages are not suitable as stable external error contracts.
