# Order Entity Guide

## Overview

`Order` is the aggregate root for a customer's sale and rental transaction. It owns the order-item collection, protects line mutations, maintains the monetary total, and controls the order lifecycle.

This guide documents the current implementation, including its business capabilities, technical design, validation rules, and explicit boundaries.

## Business Purpose

The order models a customer transaction that may contain:

- Products purchased directly.
- Products rented for a date range.
- Multiple sale and rental lines in the same transaction.
- One monetary total derived from all lines.
- A controlled lifecycle from creation to fulfillment or cancellation.

The aggregate protects transaction consistency by requiring all line changes to pass through `Order`. Callers cannot submit their own total or directly replace the item collection.

## Business Capabilities

The current aggregate can:

- Create an empty pending order for a user.
- Add a sale item while the order is pending.
- Add a rental item while the order is pending.
- Reject a rental whose start date is before an application-supplied current date.
- Require all items in one order to use the same currency.
- Change the quantity of an existing item while pending.
- Remove an existing item while pending.
- Recalculate the total after every line mutation.
- Confirm a non-empty pending order.
- Cancel a pending or confirmed order.
- Mark a confirmed order as delivered.
- Complete a delivered order.
- Reject invalid lifecycle transitions.
- Lock line-item mutations after the order leaves `Pending`.

## Aggregate Boundary

`Order` is the aggregate root and `OrderItem` is its child entity.

```text
User.Id <----------- Order.UserId
                        |
                        +--- Order.Items
                                  |
Product.Id <----------------------+- OrderItem.ProductId
```

The implementation protects this ownership boundary in several ways:

- `_items` is a private `List<OrderItem>`.
- `Items` returns an `IReadOnlyCollection<OrderItem>`.
- `OrderItem.CreateForSale` and `CreateForRental` are `internal`.
- `OrderItem.ChangeQuantity` is `internal`.
- Public callers add, change, and remove items through `Order` methods.
- `Order` recalculates `TotalPrice` after each successful mutation.
- `Order` checks its status before allowing item mutation.

These controls make it difficult for normal callers outside the domain assembly to create detached lines, bypass lifecycle rules, or leave the aggregate total stale.

## State

| Property | Type | Business meaning | Mutation |
|---|---|---|---|
| `Id` | `Guid` | Order identity and parent ID used by its items | Generated by `BaseEntity` |
| `UserId` | `Guid` | User who owns the order | Set during creation |
| `Items` | `IReadOnlyCollection<OrderItem>` | Sale and rental lines | Modified through order methods |
| `TotalPrice` | `Money?` | Sum of line totals | Recalculated internally |
| `Status` | `OrderStatus` | Current lifecycle state | Changed through lifecycle methods |
| `CreatedAt` | `DateTime` | UTC creation timestamp | Generated by `BaseEntity` |
| `IsDeleted` | `bool` | Inherited soft-delete state | Protected; no order behavior currently changes it |

## Creating an Order

Use the static factory:

```csharp
var order = Order.Create(user.Id);
```

### Creation rule

`userId` must not be `Guid.Empty`. An empty ID causes an `ArgumentException`.

### Initial state

After successful creation:

| State | Initial value |
|---|---|
| `Id` | Newly generated `Guid` |
| `UserId` | Supplied user ID |
| `Status` | `OrderStatus.Pending` |
| `Items.Count` | `0` |
| `TotalPrice` | `null` |
| `CreatedAt` | Current UTC timestamp |
| `IsDeleted` | `false` |

The factory validates the ID shape only. It does not verify that a user with that ID exists.

## Adding a Sale Item

Use `AddSaleItem`:

```csharp
var item = order.AddSaleItem(
    productId: product.Id,
    quantity: 2,
    unitPrice: new Money(1_200m, Currency.USD));
```

### Preconditions

- Order status must be `Pending`.
- Product ID must not be `Guid.Empty`.
- Quantity must be greater than zero.
- Unit price must not be null.
- Unit-price amount must be greater than zero.
- The currency must match the order's existing items, if any.

### Effects

- Creates a child item with `Type == OrderItemType.Sale`.
- Sets the item's `OrderId` to this order's ID.
- Stores the supplied product ID and unit-price snapshot.
- Sets rental duration to `null`.
- Calculates the sale line total.
- Adds the item to the private collection.
- Recalculates the order total.
- Returns the created `OrderItem`.

### Sale calculation

```text
LineTotal = UnitPrice * Quantity
```

Example:

```text
UnitPrice = USD 1,200
Quantity  = 2
LineTotal = USD 2,400
```

The aggregate does not verify product existence, current catalog price, sale eligibility, or available stock.

## Adding a Rental Item

Use `AddRentalItem`:

```csharp
var duration = new DateRange(
    new DateOnly(2026, 8, 20),
    new DateOnly(2026, 8, 23));

var item = order.AddRentalItem(
    productId: product.Id,
    duration: duration,
    quantity: 2,
    unitPricePerDay: new Money(90m, Currency.USD),
    today: new DateOnly(2026, 8, 14));
```

### Preconditions

- Order status must be `Pending`.
- Duration must not be null.
- `duration.Start` must be equal to or later than `today`.
- Product ID must not be empty.
- Quantity must be greater than zero.
- Daily unit price must not be null or zero.
- Currency must match existing order lines.

### Effects

- Creates a child item with `Type == OrderItemType.Rental`.
- Stores the rental date range.
- Treats `UnitPrice` as the price per unit per day.
- Calculates the rental line total.
- Adds the item to the order.
- Recalculates the order total.
- Returns the created item.

### Rental calculation

```text
LineTotal = UnitPricePerDay * Quantity * Duration.NumberOfDays
```

Example:

```text
UnitPricePerDay = USD 90
Quantity        = 2
NumberOfDays    = 3
LineTotal       = USD 540
```

### Why `today` is supplied by the caller

The method accepts `DateOnly today` instead of reading the system clock directly. This makes the time-dependent rule deterministic and easy to unit test.

The application layer is responsible for supplying the correct business date, including the intended time-zone policy. Passing an incorrect date can weaken or incorrectly strengthen the past-date check.

## Rental Date Semantics

`DateRange` is an immutable value object containing:

- `Start`
- `End`
- `NumberOfDays`

The constructor rejects an end date earlier than the start date.

The number of billable days is calculated as:

```text
max(1, End.DayNumber - Start.DayNumber)
```

Examples:

| Start | End | `NumberOfDays` |
|---|---|---:|
| August 20 | August 20 | 1 |
| August 20 | August 21 | 1 |
| August 20 | August 23 | 3 |

This is an elapsed-day or end-exclusive calculation with a minimum charge of one day. It does not count both boundary dates. The business should confirm this interpretation if the intended rental policy is inclusive of the return date.

## Currency Consistency

Every line in one order must use the same currency.

When an item is added:

1. The item calculates its `LineTotal`.
2. If `TotalPrice` already exists, `Order` compares its currency with the new line's currency.
3. A mismatch throws `InvalidOrderCurrencyException`.
4. The rejected item is not added, and the existing total remains unchanged.

Examples:

- An empty order may accept its first line in EUR or USD.
- After accepting a USD line, all later lines must use USD.
- Removing all items resets `TotalPrice` to `null`; a future first line may then establish either supported currency.

The rule is enforced by the aggregate in addition to `Money` addition, which also rejects mismatched currencies.

## Total-Price Management

`TotalPrice` is derived state. Callers cannot set it directly.

### Empty order

```text
Items.Count == 0
TotalPrice == null
```

### Non-empty order

The total is recalculated by starting with the first item's `LineTotal` and adding every remaining line:

```text
TotalPrice = Item1.LineTotal + Item2.LineTotal + ... + ItemN.LineTotal
```

Recalculation happens after:

- Adding a sale item.
- Adding a rental item.
- Changing an item quantity.
- Removing an item.

Removing the final item resets `TotalPrice` to `null`.

## Changing Item Quantity

Use `ChangeItemQuantity`:

```csharp
order.ChangeItemQuantity(item.Id, quantity: 4);
```

### Preconditions

- Order status must be `Pending`.
- Item ID must not be empty.
- The item must belong to this order.
- New quantity must be greater than zero.

### Effects

- The item replaces its quantity.
- The item recalculates its own line total using its existing unit price and duration.
- The order recalculates `TotalPrice`.

The operation does not revalidate product stock or availability.

## Removing an Item

Use `RemoveItem`:

```csharp
order.RemoveItem(item.Id);
```

### Preconditions

- Order status must be `Pending`.
- Item ID must not be empty.
- The item must belong to this order.

### Effects

- Removes the item from `_items`.
- Recalculates `TotalPrice`.
- Sets `TotalPrice` to `null` if the order becomes empty.

The removed item is not soft-deleted by this operation. It simply stops belonging to the in-memory aggregate collection.

## Order Lifecycle

Available statuses are:

- `Pending`
- `Confirmed`
- `Delivered`
- `Completed`
- `Canceled`

### State diagram

```text
                  Confirm()                 MarkDelivered()              Complete()
Pending ------------------------> Confirmed ------------------> Delivered ----------> Completed
   |                                  |
   | Cancel()                         | Cancel()
   +----------------------------------+------------------------> Canceled
```

### Transition table

| Method | Required current status | Target status | Additional condition |
|---|---|---|---|
| `Confirm()` | `Pending` | `Confirmed` | At least one item is required |
| `Cancel()` | `Pending` or `Confirmed` | `Canceled` | None |
| `MarkDelivered()` | `Confirmed` | `Delivered` | None |
| `Complete()` | `Delivered` | `Completed` | None |

All other transitions are rejected.

### Terminal states

`Completed` and `Canceled` are terminal under the current API:

- A completed order cannot be reopened or canceled.
- A canceled order cannot be confirmed, delivered, completed, or reopened.
- A delivered order can only be completed; it cannot be canceled.

## Confirmation

```csharp
order.Confirm();
```

Confirmation requires:

- Current status is `Pending`.
- The order contains at least one item.

An empty pending order throws `EmptyOrderException` and remains pending.

After confirmation, line composition is frozen because item mutations require `Pending` status.

## Cancellation

```csharp
order.Cancel();
```

Cancellation is allowed only from:

- `Pending`
- `Confirmed`

The model does not currently release stock, refund a payment, record a reason, or identify the actor who canceled the order.

## Delivery and Completion

```csharp
order.MarkDelivered();
order.Complete();
```

- `MarkDelivered` requires `Confirmed` and changes status to `Delivered`.
- `Complete` requires `Delivered` and changes status to `Completed`.

The aggregate does not track delivery timestamp, receiver, proof of delivery, rental return, or fulfillment state per line.

## Item Mutability by Status

The following methods call `EnsureItemsCanBeModified`:

- `AddSaleItem`
- `AddRentalItem`
- `ChangeItemQuantity`
- `RemoveItem`

They are available only in `Pending` state.

| Status | Add item | Change quantity | Remove item |
|---|---:|---:|---:|
| `Pending` | Yes | Yes | Yes |
| `Confirmed` | No | No | No |
| `Delivered` | No | No | No |
| `Completed` | No | No | No |
| `Canceled` | No | No | No |

There is no transition from `Confirmed` back to `Pending` for editing.

## Validation and Exception Reference

### Order-level failures

| Operation | Invalid condition | Exception |
|---|---|---|
| `Create` | User ID is empty | `ArgumentException` |
| Add/change/remove item | Order is not pending | `InvalidOrderStatusTransitionException` |
| Add rental item | Duration is null | `ArgumentNullException` |
| Add rental item | Start date is before supplied `today` | `InvalidDateRangeException` |
| Add item | Currency differs from current order currency | `InvalidOrderCurrencyException` |
| Change/remove item | Item ID is empty | `ArgumentException` |
| Change/remove item | Item is not found in this order | `OrderItemNotFoundException` |
| `Confirm` | Current status is not pending | `InvalidOrderStatusTransitionException` |
| `Confirm` | Order has no items | `EmptyOrderException` |
| `Cancel` | Current status is not pending or confirmed | `InvalidOrderStatusTransitionException` |
| `MarkDelivered` | Current status is not confirmed | `InvalidOrderStatusTransitionException` |
| `Complete` | Current status is not delivered | `InvalidOrderStatusTransitionException` |

### Child-item failures surfaced through order methods

| Invalid condition | Exception |
|---|---|
| Product ID is empty | `ArgumentException` |
| Quantity is zero or negative | `InvalidOrderQuantityException` |
| Unit price is null | `ArgumentNullException` |
| Unit-price amount is zero or negative | `InvalidOrderPriceException` |
| Rental has no duration | `InvalidDateRangeException` |
| Sale has a duration | `InvalidDateRangeException` |
| Date range ends before it starts | `InvalidDateRangeException` |

## Failure Atomicity

The current method order preserves aggregate state for common validation failures:

- Invalid item data fails before the new item is added.
- Currency mismatch fails before collection mutation.
- Invalid quantity fails before the existing item is changed.
- Missing item lookup fails before removal or total recalculation.
- Invalid status transition fails before status assignment.
- Empty confirmation fails before status assignment.

Therefore, these failures leave the order's existing items, total, and status unchanged.

## Technical Design

| Concern | Current design |
|---|---|
| Domain role | Aggregate root |
| Entity type | `sealed class` |
| Base type | `BaseEntity` |
| Identity | Generated `Guid` |
| Construction | Private constructor plus static `Create` factory |
| Child storage | Private `List<OrderItem>` |
| Child exposure | Read-only collection wrapper |
| Monetary state | Immutable `Money` value object |
| Rental dates | Immutable `DateRange` record |
| Lifecycle | Enum guarded by behavior methods |
| Clock dependency | Explicit `DateOnly today` argument |
| Relationships | User/product IDs rather than navigation properties |

### Encapsulation details

All aggregate state has private setters. The order API exposes commands that express business intent rather than generic property setters.

The returned `OrderItem` also has private setters. Its quantity-change method and factories are internal, preserving assembly-level aggregate control.

### Persistence consideration

Unlike `OrderItem`, `Order` currently has no parameterless constructor. Its only constructor requires `userId` and also sets `Status` to `Pending`. A future EF Core mapping must use constructor binding or another explicit materialization strategy.

Persistence also needs to map:

- The private `_items` backing field.
- The order-to-item ownership relationship.
- `Money.Amount` and `Money.Currency` for total and lines.
- `DateRange.Start` and `DateRange.End` for rental lines.
- Private setters without exposing public mutation.

## Consistency Responsibilities

### Enforced inside the aggregate

- Order starts pending.
- Item mutation is pending-only.
- Items belong to this order ID when created through order methods.
- Quantities and line prices are positive.
- Sale and rental duration shapes are valid.
- Rental start is not before supplied `today`.
- All lines share one currency.
- Total is derived from line totals.
- Empty orders cannot be confirmed.
- Status transitions follow the implemented state machine.

### Required from the application or infrastructure layer

- Verify that user and product IDs exist.
- Verify that the authenticated user may create or modify the order.
- Load and save the aggregate transactionally.
- Obtain trusted product prices instead of accepting client-supplied prices.
- Verify sale/rental product eligibility.
- Reserve, decrement, and release inventory.
- Prevent concurrent overselling or conflicting rental reservations.
- Supply a trusted business date.
- Translate exceptions into API errors.
- Coordinate payment and fulfillment systems.

## Security and Trust Boundaries

The public methods accept product IDs and prices directly. An API must not pass untrusted client prices into `AddSaleItem` or `AddRentalItem`. It should load the authoritative current product offering and supply its price to the aggregate.

Likewise, `Order.Create(userId)` does not establish authorization. The application must derive or validate `userId` from the authenticated principal and enforce administrative permissions when creating an order for another user.

## Explicitly Unsupported Capabilities

The current order model does not implement:

- Product or user existence checks.
- Inventory reservation, decrement, or restoration.
- Rental availability overlap checks.
- Duplicate-line merging.
- Price changes after adding a line.
- Rental date changes after adding a line.
- Discounts, coupons, tax, shipping, deposits, or late fees.
- Payment authorization, capture, failure, or refund.
- Shipping address or delivery method.
- Cancellation reason or actor.
- Transition timestamps or audit history.
- Per-line fulfillment, pickup, return, damage, or overdue state.
- Domain events.
- Optimistic concurrency/version tokens.
- Order deletion or restoration behavior.

These concerns must not be inferred from the methods that currently exist.

## Runtime Integration Status

The active API currently uses `Shared.Models.Order`, not `Domain.Orders.Order`.

The legacy model differs significantly:

- It has an integer ID.
- It contains one `ProductId` rather than an item collection.
- It exposes public setters.
- It stores `decimal TotalPrice` without currency.
- It stores rental dates directly on the order.
- API logic currently controls status and total calculation.

`API/API.csproj` references `Shared`, but not `Domain`. Therefore, the running API does not yet enforce this aggregate's lifecycle, currency, item-ownership, or encapsulated-total rules.

Runtime migration requires:

1. Referencing the `Domain` project from the application/API layer.
2. Creating EF Core configurations for `Order`, `OrderItem`, `Money`, and `DateRange`.
3. Replacing one-product order DTOs with multi-line contracts.
4. Creating command handlers or services that invoke aggregate methods.
5. Loading trusted products and prices before line creation.
6. Coordinating inventory and payment operations.
7. Mapping domain exceptions to stable HTTP responses.

## Usage Example

The following example demonstrates a valid mixed sale/rental workflow:

```csharp
var order = Order.Create(userId);

var saleItem = order.AddSaleItem(
    productId: saleProductId,
    quantity: 1,
    unitPrice: new Money(1_500m, Currency.USD));

var rentalPeriod = new DateRange(
    new DateOnly(2026, 8, 20),
    new DateOnly(2026, 8, 23));

var rentalItem = order.AddRentalItem(
    productId: rentalProductId,
    duration: rentalPeriod,
    quantity: 2,
    unitPricePerDay: new Money(100m, Currency.USD),
    today: new DateOnly(2026, 8, 14));

// Sale:   1,500 * 1     = USD 1,500
// Rental:   100 * 2 * 3 = USD   600
// Total:                  USD 2,100

order.ChangeItemQuantity(saleItem.Id, quantity: 2);

// New sale total: USD 3,000
// New order total: USD 3,600

order.Confirm();
order.MarkDelivered();
order.Complete();
```

After `Confirm()`, calls to add, remove, or change items throw `InvalidOrderStatusTransitionException`.

## Recommended Unit Tests

### Creation

1. Create a pending empty order with generated base-entity state.
2. Reject `Guid.Empty` as the user ID.

### Sale lines

3. Add a valid sale item and calculate its line and order totals.
4. Reject an empty product ID.
5. Reject zero and negative quantity.
6. Reject null, zero, and negative unit prices.

### Rental lines

7. Add a valid future rental item.
8. Allow a rental that starts on `today`.
9. Reject a rental that starts before `today`.
10. Reject an end date before the start date.
11. Bill a same-day rental as one day.
12. Verify multi-day line-total calculation.

### Currency and totals

13. Let the first line establish EUR or USD.
14. Accept later lines with the same currency.
15. Reject a mixed-currency line without changing state.
16. Recalculate total after changing quantity.
17. Recalculate total after removal.
18. Set total to null after removing the final item.

### Item lookup and mutation

19. Reject an empty item ID.
20. Reject an item ID that does not belong to the order.
21. Prevent direct caller mutation of the item collection.
22. Reject all item mutations after the order leaves `Pending`.

### Lifecycle

23. Reject confirmation of an empty pending order.
24. Confirm a non-empty pending order.
25. Cancel a pending order.
26. Cancel a confirmed order.
27. Mark only a confirmed order as delivered.
28. Complete only a delivered order.
29. Reject cancellation after delivery.
30. Reject all transitions from completed and canceled states.

### Integration concerns

31. Persist and reload an order without changing IDs, totals, dates, or status.
32. Verify concurrent updates do not silently overwrite aggregate state after a concurrency strategy is added.

## Current Limitations and Risks

- The rich aggregate is not used by the running API.
- There is no persistence configuration for the aggregate.
- Product prices can be supplied directly and require an application trust boundary.
- Inventory and rental availability are not checked.
- Cancellation has no payment or inventory compensation.
- There is no concurrency token.
- There are no domain events or transition audit fields.
- Rental end-date billing semantics require explicit business confirmation.
- `Order` has no parameterless persistence constructor, unlike `OrderItem`.
