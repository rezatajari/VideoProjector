# Role Entity Guide

## Overview

`Role` represents a named authorization classification that can be assigned to users by identifier. Examples could include `Admin`, `Customer`, or `Support`.

The entity is intentionally small. It provides:

- A generated `Guid` identity.
- A validated and normalized role name.
- Creation metadata inherited from `BaseEntity`.

It does not define permissions, authorize operations, own users, or issue claims. Those responsibilities require application and infrastructure services built around the role identity.

This guide describes the newer rich domain model in `Domain/Roles`. The running API currently uses a separate `Shared.Models.UserRole` enum and does not persist or consume this entity.

## Business Purpose

A role gives an authorization category a stable identity instead of embedding an unrestricted role string directly in each user.

It answers two domain questions:

- What is the stable identity of this role?
- What validated name describes the role?

Users store role IDs, so a role can be renamed or extended in a future design without changing every membership reference. The current implementation does not yet provide rename behavior or any persistence integration.

## Business Capabilities

The current role model can:

- Create a role from a typed `RoleName`.
- Generate a new role ID.
- Record the UTC creation time.
- Start with soft-delete state set to `false`.
- Preserve the role name after creation.
- Be referenced by zero or more users through its ID.

The current role model cannot:

- Rename a role.
- Define or manage permissions.
- Assign itself to a user.
- Enumerate its users.
- Check whether a role name is unique.
- Delete or restore a role through public behavior.
- Determine whether an actor is authorized.

## Position in the Domain Model

The relationship between roles and users is represented only by identifiers:

```text
Role.Id <--------- User.RolesId (zero or more)
```

`Role` does not contain a user collection, and `User` does not contain `Role` objects. Instead, `User` owns a collection of `Guid` role IDs.

This means:

- A role can exist without any user membership.
- A user can contain multiple role IDs.
- A user can contain no role IDs.
- Creating a role does not assign it to any user.
- Adding a role ID to a user does not prove that the role exists.
- Removing a role ID from a user does not modify or delete the role.

Reference existence and lifecycle consistency must be coordinated by the application layer and enforced by persistence constraints where appropriate.

## State

| Property | Type | Business meaning | How it changes |
|---|---|---|---|
| `Id` | `Guid` | Stable role identity | Generated by `BaseEntity` |
| `RoleName` | `RoleName` | Validated role name | Set during construction only |
| `CreatedAt` | `DateTime` | UTC entity creation timestamp | Generated by `BaseEntity` |
| `IsDeleted` | `bool` | Inherited soft-delete state | Initialized to `false`; no role behavior changes it |

There are no permission, description, display-order, system-role, or membership properties in the current entity.

## Creation Model

The constructor is private. Normal callers create roles through the static factory:

```csharp
public static Role Create(RoleName RoleName)
```

Example:

```csharp
var role = Role.Create(
    new RoleName("  Support  "));
```

The resulting state is:

| State | Result |
|---|---|
| `Id` | Newly generated non-empty `Guid` under normal construction |
| `CreatedAt` | Current UTC timestamp from `BaseEntity` |
| `IsDeleted` | `false` |
| `RoleName.Value` | `"Support"` |

The base constructor runs before the private role constructor, so identity and metadata are initialized automatically.

### Factory validation boundary

`Role.Create` does not validate its argument. It relies on callers to construct a valid `RoleName` before invoking the factory and stores the supplied reference directly.

The non-nullable annotation provides compile-time guidance but is not a runtime guard. A caller can bypass nullable warnings:

```csharp
var invalidRole = Role.Create(null!);
```

The current implementation accepts this call and creates a role whose `RoleName` property is null. A non-null role name is therefore an intended invariant, but `Role` does not fully enforce it at runtime.

## Role Name Rules

`RoleName` is an immutable sealed record that owns name validation and normalization.

| Input | Behavior |
|---|---|
| `null`, empty, or whitespace-only | Rejected |
| Leading or trailing whitespace | Removed with `Trim()` |
| 1 to 50 characters after trimming | Accepted |
| More than 50 characters after trimming | Rejected |
| Internal whitespace | Preserved |
| Letter casing | Preserved |
| Character alphabet | Not restricted |

Example normalization:

```csharp
var name = new RoleName("  Customer Support  ");

// name.Value == "Customer Support"
```

The type does not:

- Convert names to lowercase or uppercase.
- Collapse repeated internal spaces.
- Restrict names to a predefined vocabulary.
- Reject punctuation or non-ASCII characters.
- Translate names for display.

The 50-character limit applies after trimming. A value containing 50 characters plus surrounding spaces is accepted if the normalized value is exactly 50 characters.

## Value Equality

`RoleName` is a record, so equality is based on its normalized `Value` rather than object identity.

```csharp
var first = new RoleName("  Admin  ");
var second = new RoleName("Admin");

// first == second
```

String comparison remains case-sensitive:

```csharp
var first = new RoleName("Admin");
var second = new RoleName("admin");

// first != second
```

This value equality does not enforce uniqueness across separate `Role` entities. Two roles can be created with equal names and will still receive different IDs.

## Entity Identity and Equality

Each normal call to `Role.Create` produces a separate entity identity:

```csharp
var first = Role.Create(new RoleName("Admin"));
var second = Role.Create(new RoleName("Admin"));

// first.Id != second.Id under normal construction
// first.RoleName == second.RoleName
```

`Role` and `BaseEntity` do not override entity equality. Two role objects therefore use reference equality even if their IDs or names are equal. Code that compares persisted role identity should compare `Id` explicitly unless the project later adopts a common entity-equality strategy.

## Domain Invariants

For a role created through the intended workflow with a valid non-null `RoleName`:

| Invariant | Enforced by |
|---|---|
| Role ID is generated | `BaseEntity` |
| Creation timestamp is generated in UTC | `BaseEntity` |
| Soft-delete state starts as `false` | `BaseEntity` |
| Role-name input is not blank | `RoleName` |
| Normalized role name is at most 50 characters | `RoleName` |
| Leading and trailing name whitespace is removed | `RoleName` |
| Role name cannot be replaced through the public API | Private property setter and lack of rename behavior |

The following conditions are not enforced:

| Potential rule | Current behavior |
|---|---|
| Factory argument must be non-null at runtime | `Role.Create(null!)` succeeds |
| Role names must be unique | No repository or collection lookup occurs |
| Role names are case-insensitively unique | `Admin` and `admin` are distinct values |
| Role must contain permissions | No permission model exists |
| Role must have at least one user | A role can exist independently |
| Referenced role IDs must exist | `User.AddRole` does not load a role |
| Built-in roles cannot be changed or deleted | No built-in-role concept exists |

## Failure Reference

| Operation | Invalid condition | Exception | Message |
|---|---|---|---|
| `new RoleName(value)` | Value is null, empty, or whitespace-only | `InvalidRoleNameException` | `Role name cannot be empty.` |
| `new RoleName(value)` | Normalized value exceeds 50 characters | `InvalidRoleNameException` | `Role name is too long.` |

Validation happens before `RoleName.Value` is assigned. A failed constructor does not return a partially initialized value object.

`Role.Create` itself currently throws no domain exception and performs no null check. If runtime null protection is added later, the project should deliberately choose and document whether it uses `ArgumentNullException` or a domain-specific exception.

Application APIs should map exception types and operation context to stable validation responses instead of exposing or parsing exception message strings.

## Immutability and Encapsulation

| Member | Accessibility | Purpose |
|---|---|---|
| `Role` constructor | `private` | Directs normal construction through `Create` |
| `Role.Create` | `public static` | Creates a role from a typed name |
| `RoleName` setter | `private` | Prevents arbitrary name replacement |
| `RoleName.Value` | Getter only | Preserves the normalized name |
| `Id` setter | `protected` through `BaseEntity` | Restricts identity replacement |
| `CreatedAt` setter | `private` in `BaseEntity` | Prevents timestamp replacement |
| `IsDeleted` setter | `protected` through `BaseEntity` | Reserves soft-delete mutation for domain behavior or derived types |

Although `Role` is not declared `sealed`, its only constructor is private. A derived type cannot call that constructor, so ordinary external inheritance is not possible. Declaring the class `sealed` would make this design intent explicit but would not change current public construction behavior.

No public method currently changes any role state after creation. From a caller's perspective, the complete role is immutable.

## Assigning Roles to Users

Role membership behavior belongs to `User`, not `Role`:

```csharp
var role = Role.Create(new RoleName("Support"));
var user = User.Create(fullName, email, passwordHash, phoneNumber);

user.AddRole(role.Id);
```

`User.AddRole` currently enforces only local identifier rules:

- The role ID cannot be `Guid.Empty`.
- The same role ID cannot be added twice to one user.

`User.RemoveRole` requires a non-empty ID that is currently assigned. It allows removal of the final role.

Neither method checks:

- Whether the role exists.
- Whether the role is soft-deleted or otherwise assignable.
- Whether the acting user has authority to assign it.
- Whether the role combination is permitted.
- Whether a required baseline role remains assigned.

Those checks must be implemented by an application service or command handler using trusted persistence and authorization context.

See the [User entity guide](User.md) for the complete membership behavior.

## Authorization Boundary

A role name or role ID does not grant access by itself. A complete authorization workflow must:

1. Authenticate the user.
2. Load trusted role memberships.
3. Resolve each membership to an existing and active role.
4. Translate roles into claims, policies, or permissions.
5. Evaluate the requested operation against those policies.

The domain entity does not define how `Admin`, `Customer`, or any other name maps to permissions. Code must not authorize an operation merely because an untrusted request supplies a matching role ID or role-name string.

### Role assignment security

Role-management endpoints must prevent privilege escalation. At minimum, the application layer should:

- Require explicit authorization to create roles or modify memberships.
- Resolve IDs from server-side persistence.
- Reject nonexistent or inactive roles.
- Protect reserved administrative roles.
- Prevent unauthorized self-assignment.
- Audit security-sensitive membership changes.
- Apply concurrency controls so simultaneous updates do not lose changes.

## Persistence Considerations

The rich `Role` entity has no EF Core configuration or migration in the current repository.

A future relational mapping should account for:

| Domain state | Suggested persisted shape |
|---|---|
| `Id` | Primary-key `Guid` |
| `RoleName` | Required string with maximum length 50 |
| `CreatedAt` | Required UTC timestamp |
| `IsDeleted` | Required soft-delete flag |

`RoleName` requires an explicit value conversion, owned-type mapping, or complex-type mapping. Materialization should preserve the same validation and normalization policy used by normal construction.

### Name uniqueness

The domain currently permits duplicate role names. If business policy requires uniqueness, persistence should enforce it with a unique index as well as an application-level pre-check.

The policy must first answer:

- Is uniqueness case-sensitive?
- Are internal spaces significant?
- Can a deleted role name be reused?
- Are names global or scoped to a tenant or organization?
- Are built-in role names reserved?

The database collation and the `RoleName` equality behavior must agree with that decision. Otherwise, the application may treat two names as different while the database treats them as duplicates, or the reverse.

### User-role membership table

Because `User` stores multiple role IDs, a relational integration will normally require a join table containing:

- `UserId`.
- `RoleId`.
- A composite unique key on `(UserId, RoleId)`.
- Foreign keys to the user and role tables.

The unique constraint protects against duplicate memberships across concurrent transactions and direct database writes. Foreign keys enforce reference existence that the in-memory entity does not check.

### Deletion policy

`IsDeleted` is inherited, but `Role` exposes no delete or restore method. Before integrating soft deletion, the application must define:

- Whether a deleted role remains in existing user memberships.
- Whether deleted roles continue to produce authorization claims.
- Whether deletion is rejected while memberships exist.
- Whether built-in roles can be deleted.
- Whether a deleted role name can be reused.
- Whether global query filters hide deleted roles.

Security-sensitive authorization should fail closed when a membership points to a missing or inactive role.

### Concurrency

The entity has no version or concurrency token. Persistence should consider optimistic concurrency for role rename, deletion, permission changes, or other mutable capabilities added later.

## Runtime Integration Status

The active API does not use `Domain.Roles.Role`.

`API/API.csproj` references `Shared/Shared.csproj` but does not reference `Domain/Domain.csproj`. The current database context has no `DbSet<Role>`, and there is no rich-role EF Core configuration or role controller.

Instead, the active runtime uses:

```csharp
public enum UserRole
{
    Admin,
    Customer
}
```

Each legacy `Shared.Models.User` has exactly one `UserRole` value, which defaults to `Customer`. Registration explicitly assigns `Customer`, EF Core stores the enum as a string, and `TokenService` emits one `ClaimTypes.Role` claim using `user.Role.ToString()`.

### Rich and legacy role comparison

| Concern | Rich `Domain.Roles.Role` | Active `Shared.Models.UserRole` |
|---|---|---|
| Representation | Entity | Enum |
| Identity | Generated `Guid` | Enum value/name |
| Available names | Any valid 1-50 character name | `Admin`, `Customer` |
| Name normalization | Trims outer whitespace | Compile-time enum member |
| User cardinality | Multiple role IDs per user | Exactly one enum property |
| Default role | None | `Customer` |
| Persistence | Not mapped | String column on `Users` |
| JWT behavior | Not integrated | One role claim |
| Runtime role creation | Possible in domain memory only | Not possible; enum is compiled |
| Permissions | Not modeled | Not modeled |

The two representations are not interchangeable. Replacing an enum property with a rich role entity requires an explicit data and authorization migration.

### Integration requirements

To make the rich role model active:

1. Add a project reference from the application or API layer to `Domain`.
2. Add EF Core mapping for `Role` and `RoleName`.
3. Create a roles table and a user-role membership table.
4. Decide and enforce role-name uniqueness semantics.
5. Seed or migrate the existing `Admin` and `Customer` roles with stable IDs.
6. Map each legacy user's enum value to the corresponding membership row.
7. Change the runtime user identity model consistently; the rich user uses `Guid`, while the active legacy user uses `int`.
8. Resolve the `Customer` role during registration if it remains the default policy.
9. Update token generation to resolve all assigned roles and emit the intended claims.
10. Update authorization policies and tests for multiple role claims.
11. Add protected role-management commands or endpoints if runtime role administration is required.
12. Define deletion, reserved-role, auditing, and concurrency policies.

## End-to-End Domain Example

```csharp
var customerRole = Role.Create(
    new RoleName("  Customer  "));

var supportRole = Role.Create(
    new RoleName("Support"));

var user = User.Create(
    fullName,
    email,
    passwordHash,
    phoneNumber: null);

user.AddRole(customerRole.Id);
user.AddRole(supportRole.Id);

// customerRole.RoleName.Value == "Customer"
// supportRole.RoleName.Value  == "Support"
// user.RolesId contains both role IDs
```

The example demonstrates in-memory domain behavior only. Before assignment in a real workflow, the application must persist or load the roles, verify that they are assignable, authorize the actor, and save membership changes transactionally.

## Consistency Responsibilities

### Enforced by `RoleName`

- Reject blank input.
- Trim leading and trailing whitespace.
- Reject normalized names longer than 50 characters.
- Preserve the accepted value immutably.
- Provide case-sensitive value equality.

### Enforced by `Role`

- Generate entity identity and creation metadata through `BaseEntity`.
- Store the supplied typed name.
- Prevent public name replacement after creation.

### Enforced by `User`

- Reject an empty assigned role ID.
- Reject duplicate role IDs within one user in normal sequential use.
- Reject removal of an unassigned role ID.
- Protect the role-ID collection from direct external mutation.

### Required from application and infrastructure

- Guard against a null `RoleName` factory argument until the entity adds a runtime check.
- Enforce role-name uniqueness if required.
- Verify role existence and assignability.
- Authorize role creation and membership changes.
- Define permissions or policy mappings.
- Persist role and membership relationships.
- Protect built-in or privileged roles.
- Translate memberships into trusted claims.
- Handle deletion and dangling references safely.
- Apply transaction, auditing, and concurrency policies.

## Explicitly Unsupported Capabilities

The current rich role model does not implement:

- Role rename.
- Role description or display metadata.
- Permission entities or permission collections.
- Role inheritance or hierarchy.
- Deny rules or conflict resolution.
- Resource-scoped roles.
- Tenant- or organization-scoped roles.
- Built-in, reserved, or immutable role markers.
- Default-role designation.
- Role-name uniqueness.
- Case-insensitive canonical names.
- User navigation or membership counts.
- Role assignment or removal behavior on `Role`.
- Role-existence validation during user assignment.
- Authorization checks for role management.
- Role deletion or restoration behavior.
- Protection against deleting an assigned role.
- Domain events or audit history beyond creation time.
- Optimistic concurrency or version tracking.
- Repository interfaces or persistence mappings.
- API endpoints for role administration.
- JWT, claims, or policy generation.

## Recommended Unit Tests

### Role creation

1. Creating a role generates a non-empty `Guid`.
2. `CreatedAt` is a UTC timestamp close to creation time.
3. `IsDeleted` starts as `false`.
4. The role retains the supplied `RoleName` reference.
5. A new role has no implicit user membership.
6. Two roles with the same name receive different IDs.

### Role name

7. A normal role name is preserved.
8. Leading and trailing whitespace is trimmed.
9. Internal spaces are preserved.
10. Letter casing is preserved.
11. Null, empty, and whitespace-only input is rejected.
12. A normalized 50-character name is accepted.
13. A normalized 51-character name is rejected.
14. Equal normalized names compare equal as value objects.
15. Names that differ only by case compare unequal under current rules.

### Factory guard

16. Add a test requiring `Role.Create(null!)` to fail after a runtime null guard is introduced.

This test describes the intended invariant and fails against the current implementation because the factory accepts a null reference.

### User membership

17. A user can add the ID of a created role.
18. A user can add multiple distinct role IDs.
19. A user rejects a duplicate role ID.
20. Removing a role ID from a user does not modify the role entity.
21. Application logic rejects assignment of a nonexistent role.
22. Application logic rejects assignment of an inactive role.
23. Application authorization rejects an unauthorized privileged-role assignment.

### Persistence and runtime integration

24. A role and its typed name round-trip through persistence.
25. The database rejects duplicate memberships.
26. The database applies the chosen role-name uniqueness semantics.
27. Legacy `Admin` and `Customer` values migrate to the intended role IDs.
28. Registration assigns the intended default role membership.
29. Token generation emits every intended role claim without trusting client input.
30. Deleted or missing roles do not grant authorization.

## Current Limitations and Risks

- `Role.Create` accepts a runtime null `RoleName` reference.
- Duplicate role names are allowed.
- Name equality is case-sensitive, so `Admin` and `admin` are different domain values.
- The role entity is not integrated into the active API or database.
- The active enum supports one role per user, while the rich domain supports multiple role IDs.
- The rich and legacy user models use incompatible `Guid` and `int` identities.
- The entity does not define permissions or authorization policies.
- User assignment does not verify role existence or active state.
- The entity has no rename, delete, or restore behavior.
- Soft-delete state exists without a defined authorization or membership policy.
- There is no protection for built-in or privileged roles.
- There is no audit trail for security-sensitive role changes.
- There is no optimistic concurrency token.
- There is no persistence mapping for the private constructor and typed name.
