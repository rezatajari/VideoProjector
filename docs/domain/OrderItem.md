# OrderItem Entity Guide

## Overview

`OrderItem` represents one priced product line inside an `Order`. A line is either a direct sale or a time-based rental. It captures the product reference, line type, quantity, unit-price snapshot, optional rental duration, and calculated line total.

`OrderItem` is not intended to be an independent aggregate root. Its factories and mutation method are `internal`, while the owning `Order` exposes the public business operations used to create, change, and remove lines.

This guide describes the business behavior and technical constraints implemented by the current source code. It distinguishes rules enforced by `OrderItem` itself from rules enforced by the parent `Order` or required from application services.

## Business Purpose

An order item answers the line-level questions in a transaction:

- Which product is being ordered?
- Is it being purchased or rented?
- How many units are involved?
- What price was captured for each unit?
- If rented, what period is being charged?
- What is the resulting amount for this line?

The entity protects the relationship between these values. For example, a rental line must contain a duration, a sale line must not contain one, and the line total is calculated rather than accepted from a caller.

## Business Capabilities

The current entity can:

- Represent a sale line.
- Represent a rental line.
- Capture an order ID and product ID.
- Capture a strictly positive quantity.
- Capture a strictly positive unit price.
- Distinguish sale and rental pricing semantics.
- Require a duration for rental lines.
- Forbid a duration on sale lines.
- Calculate a sale total from price and quantity.
- Calculate a rental total from daily price, quantity, and billable days.
- Report whether the line is a rental through `IsRental`.
- Change quantity and recalculate the line total.
- Preserve its type, product, price, currency, and rental duration after creation.

## Position Inside the Order Aggregate

```text
Order
  |
  +--- OrderItem
         |--- OrderId   ------> Order.Id
         |--- ProductId ------> Product.Id
         |--- Type
         |--- Quantity
         |--- UnitPrice
         |--- Duration
         +--- LineTotal
```

`Order` is the effective aggregate root:

- It owns the private item collection.
- It creates items through internal named factories.
- It checks that item mutations are allowed only while the order is pending.
- It checks that all items use the same currency.
- It recalculates the order total when a line is added, changed, or removed.

`OrderItem` owns line-level consistency:

- Valid parent and product ID shapes.
- Positive quantity.
- Positive unit price.
- Correct duration shape for the selected line type.
- Correct line-total calculation.

## State

| Property | Type | Business meaning | How it changes |
|---|---|---|---|
| `Id` | `Guid` | Identity of this order line | Generated by `BaseEntity` |
| `OrderId` | `Guid` | ID of the owning order | Set during creation only |
| `ProductId` | `Guid` | ID of the referenced product | Set during creation only |
| `Type` | `OrderItemType` | `Sale` or `Rental` | Set during creation only |
| `Duration` | `DateRange?` | Rental period; null for a sale | Set during creation only |
| `Quantity` | `int` | Number of units on the line | Set at creation; changeable internally |
| `UnitPrice` | `Money` | Sale price per unit or rental price per unit per day | Set during creation only |
| `LineTotal` | `Money` | Calculated charge for the complete line | Calculated at creation and quantity change |
| `IsRental` | `bool` | Derived indication that `Type` is `Rental` | Computed from `Type` |
| `CreatedAt` | `DateTime` | UTC entity creation timestamp | Generated by `BaseEntity` |
| `IsDeleted` | `bool` | Inherited soft-delete state | Protected; no item behavior changes it |

## Supported Item Types

`OrderItemType` currently defines two values:

| Type | Unit-price meaning | Duration | Formula |
|---|---|---|---|
| `Sale` | Price per purchased unit | Must be `null` | `UnitPrice * Quantity` |
| `Rental` | Price per rented unit per day | Required | `UnitPrice * Quantity * NumberOfDays` |

An item cannot switch between sale and rental after creation. There is no public or internal behavior that changes `Type`.

## Creation Model

The entity has no public factory or public constructor. It exposes these assembly-level factories:

```csharp
internal static OrderItem CreateForSale(
    Guid orderId,
    Guid productId,
    int quantity,
    Money unitPrice)
```

```csharp
internal static OrderItem CreateForRental(
    Guid orderId,
    Guid productId,
    DateRange duration,
    int quantity,
    Money unitPricePerDay)
```

Application code outside the `Domain` assembly should create lines through:

- `Order.AddSaleItem(...)`
- `Order.AddRentalItem(...)`

This keeps order status, currency consistency, collection ownership, and aggregate-total recalculation around the line-level rules.

## Creating a Sale Line

The normal public workflow is:

```csharp
var item = order.AddSaleItem(
    productId: product.Id,
    quantity: 3,
    unitPrice: new Money(250m, Currency.USD));
```

Internally, `Order` calls `OrderItem.CreateForSale` with its own ID.

### Sale-line result

| Property | Result |
|---|---|
| `OrderId` | Owning order's ID |
| `ProductId` | Supplied product ID |
| `Type` | `OrderItemType.Sale` |
| `Duration` | `null` |
| `Quantity` | Supplied positive quantity |
| `UnitPrice` | Supplied sale-price snapshot |
| `LineTotal` | `UnitPrice * Quantity` |
| `IsRental` | `false` |

### Sale calculation example

```text
UnitPrice = USD 250
Quantity  = 3

LineTotal = 250 * 3
          = USD 750
```

## Creating a Rental Line

The normal public workflow is:

```csharp
var duration = new DateRange(
    new DateOnly(2026, 8, 20),
    new DateOnly(2026, 8, 24));

var item = order.AddRentalItem(
    productId: product.Id,
    duration: duration,
    quantity: 2,
    unitPricePerDay: new Money(80m, Currency.USD),
    today: new DateOnly(2026, 8, 14));
```

Internally, `Order` checks the start date and calls `OrderItem.CreateForRental`.

### Rental-line result

| Property | Result |
|---|---|
| `OrderId` | Owning order's ID |
| `ProductId` | Supplied product ID |
| `Type` | `OrderItemType.Rental` |
| `Duration` | Supplied date range |
| `Quantity` | Supplied positive quantity |
| `UnitPrice` | Supplied daily price per unit |
| `LineTotal` | `UnitPrice * Quantity * NumberOfDays` |
| `IsRental` | `true` |

### Rental calculation example

```text
UnitPricePerDay = USD 80
Quantity        = 2
NumberOfDays    = 4

LineTotal = 80 * 2 * 4
          = USD 640
```

The property is named `UnitPrice` for both line types. For a rental item, its business meaning is specifically the daily price for one unit.

## Rental Duration Semantics

`Duration` uses the immutable `DateRange` value object.

```csharp
var duration = new DateRange(startDate, endDate);
```

`DateRange` enforces:

- `startDate` may equal `endDate`.
- `startDate` must not be later than `endDate`.
- `NumberOfDays` is always at least one.

The current calculation is:

```text
NumberOfDays = max(1, End.DayNumber - Start.DayNumber)
```

Examples:

| Start | End | Difference | Billable days |
|---|---|---:|---:|
| August 20 | August 20 | 0 | 1 |
| August 20 | August 21 | 1 | 1 |
| August 20 | August 24 | 4 | 4 |

This treats the end date as an end boundary and guarantees a minimum one-day charge. It does not charge both the start and end dates inclusively.

### Temporal validation boundary

`OrderItem` validates that a rental has a duration, but it does not know whether that duration begins in the past. The past-date rule belongs to `Order.AddRentalItem`, which compares `duration.Start` with the supplied `today` value.

Consequently, code inside the `Domain` assembly that calls `CreateForRental` directly could create a past-dated rental unless it performs the same contextual check. The intended path is through `Order`.

## Line-Total Calculation

The entity centralizes total calculation in one private method:

```csharp
private static Money CalculateLineTotal(
    Money unitPrice,
    int quantity,
    DateRange? duration)
```

Its behavior is equivalent to:

```text
base total = unit price * quantity

if duration is null:
    line total = base total
else:
    line total = base total * duration.NumberOfDays
```

This method is used both:

- During initial construction.
- After a quantity change.

The caller cannot supply `LineTotal`, so a normal creation or mutation cannot introduce a total that disagrees with the entity's formula.

## Money and Currency Behavior

`UnitPrice` and `LineTotal` use the immutable `Money` record. A `Money` contains:

- A decimal `Amount`.
- A `Currency` enum value.

Supported currencies are currently:

- `EUR`
- `USD`

Multiplication returns a new `Money` with:

- The amount multiplied by a positive integer.
- The original currency preserved.

Therefore, `LineTotal.Currency` always matches `UnitPrice.Currency` in a normally created item.

### Layered price validation

`Money` and `OrderItem` enforce different constraints:

| Value | `Money` behavior | `OrderItem` behavior |
|---|---|---|
| Negative amount | Rejected by `Money` with `InvalidMoneyAmountException` | Normally cannot reach item creation |
| Zero amount | Accepted by `Money` | Rejected with `InvalidOrderPriceException` |
| Positive amount | Accepted | Accepted |

This means zero can be meaningful as a general monetary value but is not valid as an order-line price.

### Cross-line currency rule

`OrderItem` does not compare itself with other items. The parent `Order` rejects a new item when its line-total currency differs from the existing order currency.

## Changing Quantity

Quantity is changed through the parent aggregate:

```csharp
order.ChangeItemQuantity(item.Id, quantity: 5);
```

`Order` finds the child and invokes the internal method:

```csharp
internal void ChangeQuantity(int quantity)
```

### Preconditions

- The owning order must be `Pending` when using the public aggregate API.
- The item must exist in that order.
- The new quantity must be greater than zero.

### Effects

- Replaces `Quantity` with the new value.
- Recalculates `LineTotal` from the unchanged price and duration.
- Causes `Order` to recalculate `TotalPrice`.

### Sale example

```text
Before: USD 100 * 2 = USD 200
After:  USD 100 * 5 = USD 500
```

### Rental example

```text
Daily price = USD 100
Days        = 3

Before: 100 * 2 * 3 = USD 600
After:  100 * 5 * 3 = USD 1,500
```

Changing quantity does not change:

- `Id`
- `OrderId`
- `ProductId`
- `Type`
- `Duration`
- `UnitPrice`
- `CreatedAt`
- `IsDeleted`

## Derived Rental Indicator

`IsRental` is not stored separately:

```csharp
public bool IsRental => Type == OrderItemType.Rental;
```

This avoids contradictory state such as `Type == Sale` while a stored rental flag is true.

For valid enum values:

| `Type` | `IsRental` |
|---|---:|
| `Sale` | `false` |
| `Rental` | `true` |

There is no separate `IsSale` property.

## Domain Invariants

The following conditions must hold for every normally created item:

| Invariant | Enforced by |
|---|---|
| Item ID is generated | `BaseEntity` |
| Creation timestamp is UTC | `BaseEntity` |
| Order ID is not empty | `OrderItem.Validate` |
| Product ID is not empty | `OrderItem.Validate` |
| Quantity is greater than zero | `OrderItem.ValidateQuantity` |
| Unit price is not null | `OrderItem.Validate` |
| Unit-price amount is greater than zero | `OrderItem.Validate` |
| Sale duration is null | Private constructor |
| Rental duration is not null | Factory and private constructor |
| Date-range start is not after its end | `DateRange` |
| Billable days are at least one | `DateRange` |
| Line-total currency matches unit-price currency | `Money` multiplication |
| Line total follows the type-specific formula | `CalculateLineTotal` |
| Rental indicator agrees with type | Computed `IsRental` property |

Additional aggregate-level invariants are enforced by `Order`:

- All lines in one order use the same currency.
- Lines can be added or changed only while the order is pending.
- A rental start date is not before the supplied current date.
- The parent total equals the sum of line totals.

## Validation and Exception Reference

| Invalid condition | Detection point | Exception |
|---|---|---|
| Rental duration argument is null | `CreateForRental` | `ArgumentNullException` |
| Order ID is `Guid.Empty` | `Validate` | `ArgumentException` |
| Product ID is `Guid.Empty` | `Validate` | `ArgumentException` |
| Quantity is zero or negative | `ValidateQuantity` | `InvalidOrderQuantityException` |
| Unit price is null | `Validate` | `ArgumentNullException` |
| Unit-price amount is zero | `Validate` | `InvalidOrderPriceException` |
| Negative amount is used to construct `Money` | `Money` constructor | `InvalidMoneyAmountException` |
| Rental item has no duration | Private constructor | `InvalidDateRangeException` |
| Sale item has a duration | Private constructor | `InvalidDateRangeException` |
| Date-range end precedes start | `DateRange` constructor | `InvalidDateRangeException` |
| Rental starts before supplied `today` | `Order.AddRentalItem` | `InvalidDateRangeException` |
| New line uses a different currency | `Order.AddItem` | `InvalidOrderCurrencyException` |
| Quantity change is attempted after pending state | `Order.ChangeItemQuantity` | `InvalidOrderStatusTransitionException` |
| Quantity-change item ID is empty | `Order.GetItem` | `ArgumentException` |
| Quantity-change item is not in the order | `Order.GetItem` | `OrderItemNotFoundException` |

The first failure encountered is thrown. For example, item construction validates IDs and quantity before checking the sale/rental duration combination.

## Failure Atomicity

The item avoids partial mutation in its available workflows:

- Construction completes validation before assigning domain state.
- `ChangeQuantity` validates the new quantity before assigning it.
- Line-total calculation occurs immediately after quantity assignment and receives validated positive multipliers.

For ordinary validated values, an invalid quantity leaves both `Quantity` and `LineTotal` unchanged.

At the aggregate level:

- A currency mismatch is detected before the new item is added.
- A missing item is detected before mutation.
- Order status is checked before quantity change.
- The order total is recalculated only after a successful line change.

## Encapsulation and Accessibility

| Member | Accessibility | Reason |
|---|---|---|
| Main constructor | `private` | Centralizes creation invariants |
| Parameterless constructor | `private` | Supports materialization tooling |
| Sale/rental factories | `internal` | Keeps normal creation inside domain assembly |
| `ChangeQuantity` | `internal` | Keeps mutation under aggregate coordination |
| Domain-property setters | `private` | Prevents arbitrary caller mutation |
| `IsRental` | Public getter | Exposes derived information without state mutation |

The boundary is enforced at the assembly level, not strictly at the `Order` class level. Any code compiled into the `Domain` assembly can call the internal factories or `ChangeQuantity`. Such code must preserve aggregate rules, especially status checks and total recalculation.

## Immutability Profile

After creation, most line state is intentionally fixed:

| State | Mutable after creation? |
|---|---:|
| Order reference | No |
| Product reference | No |
| Sale/rental type | No |
| Rental duration | No |
| Unit price | No |
| Currency | No |
| Quantity | Yes, internally |
| Line total | Recalculated only from quantity change |

This creates a price snapshot. Later changes to a product's catalog price do not automatically alter existing order items.

There is no behavior for repricing a line, changing its rental dates, or replacing its product. The current workflow is to remove the pending item and add a new one.

## Persistence Considerations

`OrderItem` contains a private parameterless constructor for persistence materialization:

```csharp
private OrderItem()
{
}
```

The null-forgiving initializers on `UnitPrice` and `LineTotal` suppress nullable compiler warnings for this materialization path:

```csharp
public Money UnitPrice { get; private set; } = null!;
public Money LineTotal { get; private set; } = null!;
```

They do not provide runtime values. Persistence must populate both properties correctly.

An EF Core mapping for this entity should preserve:

- The `Order` ownership relationship and required `OrderId`.
- Required `ProductId`.
- The `OrderItemType` enum.
- Nullable duration for sales and required duration for rentals.
- `Money.Amount` and `Money.Currency` for both monetary properties.
- The private setters and aggregate collection backing field.
- Entity identity and creation metadata.

### Database constraints worth adding

The persistence layer should mirror key domain invariants where practical:

- `OrderId` is required.
- `ProductId` is required.
- `Quantity > 0`.
- Unit-price amount is greater than zero.
- Line-total amount is greater than zero.
- Type is one of the defined enum values.
- Rental rows contain dates; sale rows do not.
- End date is not before start date.
- Unit-price and line-total currencies match.

The constructor accepts an `OrderItemType`, but it does not explicitly reject undefined numeric enum values. Named factories always pass a defined value. A database constraint is important if persistence can contain arbitrary numeric values.

### Derived-total persistence

`LineTotal` is derived from other line state but is also stored as entity state. If it is persisted, the mapping and update workflow must prevent database values from drifting away from the domain formula.

Possible integration strategies include:

- Persist the calculated value and update only through the aggregate.
- Recalculate during materialization validation.
- Use a database computed expression if its rental semantics can be represented reliably.

The current domain project does not choose one of these strategies.

## Business Meaning of Captured Price

The item accepts a `Money` supplied by its caller. It does not load the product or derive a price itself.

The application layer should treat `UnitPrice` as a trusted snapshot selected from the product's current sale or rental offer. A public API must not allow a client to choose an arbitrary amount and pass it directly into the aggregate.

Before adding a line, application logic should verify:

- The product exists.
- The product is active or otherwise orderable.
- The requested line type is supported by that product.
- The authoritative sale or daily rental price is used.
- The requested quantity is available.
- The selected currency is allowed for the order and product.

## Consistency Responsibilities

### Enforced by `OrderItem`

- Valid non-empty order and product ID shapes.
- Positive quantity.
- Non-null and positive unit price.
- Sale/rental duration consistency.
- Type-specific line-total calculation.
- Recalculation after quantity change.
- Stable product, type, duration, unit price, and currency.

### Enforced by `Order`

- Item creation occurs only while pending.
- Rental does not start in the past relative to supplied `today`.
- All lines use one currency.
- Quantity changes occur only while pending.
- Changed item belongs to the order.
- Aggregate total is recalculated after line changes.

### Required from application and infrastructure

- Existence of the order, product, and user.
- Authorization to modify the order.
- Authoritative product pricing.
- Product sale/rental eligibility.
- Stock and rental availability.
- Transactional persistence.
- Concurrency conflict handling.
- Exception-to-API response mapping.

## Security and Trust Boundaries

`ProductId`, `Quantity`, and price all enter through caller arguments. The domain validates their shape and mathematical validity, but not their authority.

The application layer must prevent:

- Price tampering by clients.
- Adding products the customer is not allowed to order.
- Bypassing product availability rules.
- Modifying another user's order.
- Supplying an untrusted `today` value to rental creation.
- Concurrent updates that overwrite a recalculated total.

## Explicitly Unsupported Capabilities

The current item model does not implement:

- Product existence validation.
- Product name, SKU, or description snapshots.
- Product sale/rental eligibility checks.
- Stock reservation or decrement.
- Rental-overlap availability checks.
- Maximum quantity rules.
- Quantity measured in units other than integer pieces.
- Price-list lookup or dynamic pricing.
- Price changes after creation.
- Rental-duration changes after creation.
- Product replacement after creation.
- Discounts, taxes, fees, deposits, or shipping allocation.
- Per-line payment state.
- Per-line fulfillment, pickup, return, damage, or overdue state.
- Cancellation or removal reason.
- Soft-delete or restore behavior.
- Domain events.
- Audit history beyond `CreatedAt`.
- Optimistic concurrency/version tracking.

## Runtime Integration Status

The active API currently references the legacy `Shared` model rather than the rich entities in `Domain`. `API/API.csproj` does not currently reference `Domain/Domain.csproj`.

As a result, the running API does not automatically use this `OrderItem` entity or enforce its line-type, positive-price, duration-shape, encapsulated-total, and aggregate-ownership rules.

Integrating this entity requires:

1. Referencing the domain project from an application/API layer.
2. Introducing multi-line order request and response contracts.
3. Mapping `Order` and `OrderItem` to persistence.
4. Mapping `Money`, `Currency`, and `DateRange` correctly.
5. Loading trusted product offerings before line creation.
6. Invoking item behavior through the `Order` aggregate.
7. Translating domain exceptions into stable validation responses.

## End-to-End Usage Example

```csharp
var order = Order.Create(userId);

var saleItem = order.AddSaleItem(
    productId: projectorId,
    quantity: 2,
    unitPrice: new Money(1_250m, Currency.USD));

// saleItem.Type      == OrderItemType.Sale
// saleItem.IsRental  == false
// saleItem.Duration  == null
// saleItem.LineTotal == Money(2_500, USD)

var duration = new DateRange(
    new DateOnly(2026, 8, 20),
    new DateOnly(2026, 8, 23));

var rentalItem = order.AddRentalItem(
    productId: screenId,
    duration: duration,
    quantity: 2,
    unitPricePerDay: new Money(50m, Currency.USD),
    today: new DateOnly(2026, 8, 14));

// rentalItem.Type              == OrderItemType.Rental
// rentalItem.IsRental          == true
// rentalItem.Duration          == duration
// rentalItem.Duration.NumberOfDays == 3
// rentalItem.LineTotal         == Money(300, USD)
// order.TotalPrice             == Money(2_800, USD)

order.ChangeItemQuantity(rentalItem.Id, quantity: 3);

// rentalItem.LineTotal == Money(450, USD)
// order.TotalPrice     == Money(2_950, USD)
```

The equality comments above describe value equality of the immutable `Money` record; actual application assertions should compare `Amount` and `Currency` or construct an equivalent `Money` value.

## Recommended Unit Tests

### Sale creation

1. Create a sale item through `Order` with expected IDs and type.
2. Set `Duration` to null and `IsRental` to false.
3. Calculate line total from unit price and quantity.
4. Preserve the supplied currency.

### Rental creation

5. Create a rental item through `Order` with expected IDs and type.
6. Retain the supplied immutable duration.
7. Set `IsRental` to true.
8. Calculate total from daily price, quantity, and billable days.
9. Bill same-day rental as one day.
10. Verify end-exclusive multi-day semantics.

### Identity and input validation

11. Reject an empty order ID in direct domain-assembly factory tests.
12. Reject an empty product ID.
13. Reject null unit price.
14. Reject zero unit price at item creation.
15. Reject negative amount at `Money` creation.
16. Reject zero and negative quantity.
17. Reject null rental duration.
18. Reject a date range whose end precedes its start.

### Type and duration invariants

19. Verify sale factory creates no duration.
20. Verify rental factory requires a duration.
21. Verify type and rental indicator cannot diverge through the public API.
22. Verify no public API can change type, duration, product, or unit price.

### Quantity mutation

23. Recalculate a sale line after quantity change.
24. Recalculate a rental line after quantity change.
25. Leave quantity and line total unchanged after an invalid quantity attempt.
26. Make the parent order recalculate its total after a successful change.
27. Reject quantity changes after the order leaves `Pending`.

### Aggregate coordination

28. Use the parent order ID for every created line.
29. Reject mixed-currency lines before collection mutation.
30. Reject past rental starts through `Order.AddRentalItem`.
31. Reject changes for an item ID not owned by the order.
32. Prevent external collection mutation.

### Persistence

33. Round-trip all line state without changing calculated values.
34. Materialize sale rows with null duration.
35. Materialize rental rows with complete duration values.
36. Reject or detect undefined stored item-type values.
37. Detect persisted line totals that disagree with the formula.

## Current Limitations and Risks

- The entity is not integrated into the active API persistence model.
- The application must establish a trusted price source.
- The item does not verify product eligibility, stock, or rental availability.
- Past-date validation exists in `Order`, not in the internal rental factory.
- Internal access protects the boundary only at assembly level.
- Undefined enum values are not explicitly rejected by the constructor.
- Persisted `LineTotal` can drift if infrastructure bypasses domain behavior.
- Decimal amounts have no explicit scale or currency-rounding policy in the domain.
- There is no upper quantity or amount limit; extreme decimal multiplication can overflow.
- The rental end-date billing convention must match the intended business policy.
- No concurrency token protects simultaneous quantity updates.
